## Summary

A plugin may supply lists of addresses to deny. It declares kinds of source
in a `blocklist` block, each with a code, a name, a configuration form and a
default refresh interval, and requests `network`. A person creates sources
of those kinds; the host calls `blocklist.fetch` on the interval of each
source, validates every entry as an address or a CIDR network, writes
`deny` rules to a file of its own in the nginx configuration directory and
reloads nginx when the file changed. The person includes the file where the
list should apply.

## Motivation

Blocking known abusers at nginx is cheap and effective, and the lists exist:
threat feeds, reputation services, ban lists shared between servers. Each
has its own API and format, so the core cannot ship them, while turning a
list into `deny` rules, scheduling refreshes and reloading nginx safely is
the same for every one of them and belongs in the host.

## Design

### Manifest

```json
{
  "capabilities": ["security.blocklist"],
  "permissions": ["network"],
  "blocklist": {
    "sources": [
      {
        "code": "threatfeed",
        "name": "ThreatFeed",
        "refresh_seconds": 900,
        "configuration": { "fields": [{ "key": "api_key", "display_name": "API key", "required": true, "secret": true }] }
      }
    ]
  }
}
```

The form reuses `ConfigurationSchema` from RFC 0002 and codes follow NAME-10
in a namespace of their own. `refresh_seconds` is the default interval of a
new source of the kind: absent or `0` means an hour, and anything shorter
than a minute is invalid, since every change costs a reload.

### Method

| Method | Params | Result |
| --- | --- | --- |
| `blocklist.fetch` | `{ source, config }` | `{ entries: [{ cidr, reason }], ttl_seconds }` |

The answer is always the complete list, so the host never has to reconcile
deltas, and an error keeps the list the host has while an empty list denies
nothing (BLOCKLIST-6): a source that is down must not unblock everybody.
`ttl_seconds` lets a source ask for an earlier refresh. There is no
`validate` method: a fetch with the configuration is the only meaningful
check, and the person can run it from the page.

### Reference host

* `internal/security/blocklist` holds the source kind registry (`Source`,
  `RegisterSource`, `Kinds`), turns an answer into the file (`Render`) and
  runs the refreshes (`Runner`). `internal/plugin/capability.RegisterBlocklist`
  registers the plugin manager as a source; a kind is stored as
  `plugin:<code>` and its plugin is resolved at every call.
* `internal/config.GeneratedWriter` writes a generated file: under the
  configuration apply lock it compares the new content with the file, and
  only when they differ it snapshots the file, replaces it atomically through
  the nginx target filesystem, runs `nginx -t` and reloads. A failed test
  restores the snapshot and skips the reload; a failed reload restores the
  snapshot and reloads again.
* `model.BlocklistSource { name, kind, config, refresh_seconds, enabled,
  last_run_at, next_run_at, last_status, last_message, entry_count }`, with
  `config` encrypted at rest. Migration `20260923000004` creates the table.
* The runner checks every 30 seconds for enabled sources whose `next_run_at`
  passed and refreshes them concurrently, one run per source at a time. A
  successful run is due again after `refresh_seconds`, or after
  `ttl_seconds` when that is shorter but at least 60; a failed run after
  five minutes or `refresh_seconds`, whichever is shorter. `blocklist.fetch`
  has 60 seconds.
* Every entry is parsed with `net/netip`; the network address of a prefix is
  used, IPv4-mapped IPv6 addresses become IPv4, entries covering every
  address, zones and anything else are dropped, duplicates removed and the
  rest sorted, at most 100000 kept. `last_message` reports how many entries
  were written and dropped and whether nginx was reloaded.
* The file is `<nginx conf dir>/blocklists/<id>.conf` with a
  `# generated by nginx-ui` header and one `deny` line per entry. The page
  shows `include blocklists/<id>.conf;` with a copy button: nginx resolves a
  relative `include` against the directory of `nginx.conf`, which is the
  directory nginx-ui writes to unless the configuration directory setting
  points elsewhere, so the absolute path is shown as well.
* `GET/POST/DELETE /api/blocklist_sources` (CRUD; changes need an
  interactive administrator with a secure session and are closed in demo
  mode), `GET /api/blocklist_sources/kinds` and
  `POST /api/blocklist_sources/:id/refresh`. Saving checks the kind, the
  required fields (55206, "blocklist source config field {0} is invalid:
  {1}") and the interval (55209); a kind whose plugin is gone fails with
  55205. Deleting a source removes its file with a configuration test first
  and is refused with 55213 while nginx still includes it.
* The "Blocklists" page next to the upstream page lists the sources with
  their last result and manages them with a kind selector,
  `PluginConfigForm`, the interval, a refresh button and the include line.

## Compatibility

A new optional capability, block and service; nothing existing changes
meaning (VER-1). The new table does not touch existing ones, and no existing
nginx file is changed: the generated files take effect only where a person
includes them.

## Alternatives considered

* **Writing the rules into the site files directly.** Every refresh would
  rewrite files people edit by hand, and a list could not be shared between
  sites.
* **`geo` maps instead of `deny` lines.** Faster for very long lists, but
  they need an `if` or a `map` in each server block and a person to
  understand them; `deny` works wherever `include` does. A future version can
  add a `geo` output next to it.
* **Delta updates.** Smaller answers, but the host would have to keep and
  reconcile state, and a lost update would silently leave an address
  blocked or unblocked.

## Security considerations

A blocklist decides who can reach a site, so the host treats the answer as
untrusted: only parsed addresses and networks reach the file, never other
text of the answer, and entries that would deny everyone are dropped
(SEC-15). The file only takes effect where a person includes it, every
reload is preceded by a configuration test, and a failed test puts the
previous file back. Source values are credentials: encrypted at rest, masked
in the form and never logged. Changes need an interactive administrator with
a secure session and are closed in demo mode.

## Future work

* An allowlist that always wins over every source.
* A `geo` output for very long lists.
* Showing the reasons of the last answer on the page.
